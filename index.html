Your tablet is already on WiFi just to load this page — this field isn't about connecting to WiFi. It's a separate restriction: browsers block a webpage from directly fetching most other sites' content (CORS), no matter how good your connection is. Buddie sends search-bar queries here first; run a small local proxy on your network to fetch pages for Buddie. Leave blank to use direct fetch (works for open APIs only, like Wikipedia/arXiv).
A browser tab cannot reach the Tor network on its own — there's no such thing as "Tor from HTML." This field only points Buddie at a bridge you run locally (e.g. a small script proxying through Tor's SOCKS port), same pattern as the scraper endpoint above, kept separate and under its own hard rules:
• Only fires when you tap the 🧅 Tor toggle next to the search bar — off by default, never turns itself on.
• Sends your typed query terms exactly as written — no expansion, no related-topic guessing.
• Text only. Buddie strips markup and keeps plain text; it never fetches, follows, or saves images, video, binaries, or file downloads of any kind, from this endpoint or any other.
• Every result is scanned by a built-in explicit-content filter before it touches storage. Anything flagged is discarded immediately — only a "blocked" note is logged, the flagged text itself is never kept, shown, or written anywhere.
• Nothing from this endpoint is auto-saved. Results land in a separate review queue (Memory tab) and only enter Pre-Verified if you personally tap "Keep" on that specific item.
You're responsible for what your own bridge script does and for the legality of using it where you live — Buddie's part is limited to the rules above.

Add as many keys from as many providers as you have. Every reply request tries the next healthy key in rotation; a key that errors out (bad key, rate-limited, or blocked by the browser's CORS rules — some providers don't allow direct browser calls at all) gets put on a cooldown and skipped automatically, so only keys that actually connect stay in active use. If every key is cooling down or none are configured, Buddie transparently uses the local on-device model instead — nothing ever just fails silently.
⚠️ Keys are stored only in this device's local IndexedDB (same as everything else in this app) — never written into the HTML file itself, never sent anywhere except straight to that provider's own API. Still, this is a browser page holding raw API keys in memory to call providers directly — treat it like any other place you'd paste a real dev key, and use keys you're comfortable exposing client-side (e.g. capped-spend/test keys), not a production key.
